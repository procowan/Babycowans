# Babycowans Protocol SDK Specification

## 1. Purpose

The Babycowans SDK provides the canonical developer interface for interacting with the Babycowans Protocol.

The SDK abstracts:

- PDA derivation
- account validation
- transaction construction
- instruction encoding
- IDL loading
- account fetching
- event decoding

Applications should never construct protocol instructions manually.

---

## 2. Design Goals

The SDK must satisfy the following goals.

### Simple

Common operations require only a few lines of code.

### Deterministic

The SDK always derives identical addresses from identical inputs.

### Type Safe

All public interfaces expose strongly typed objects.

### Stable

Minor protocol updates must not require SDK rewrites.

### Zero Business Logic

Business rules remain inside the on-chain program.

The SDK never duplicates protocol logic.

---

## 3. Package

The official package name is:

```text
@babycowans/core-sdk
```

The SDK is the canonical client library for:

- Node.js
- TypeScript
- JavaScript

Additional language SDKs may be developed in future protocol versions.

---

## 4. Installation

```bash
npm install @babycowans/core-sdk
```

or

```bash
yarn add @babycowans/core-sdk
```

---

## 5. SDK Layers

The SDK consists of the following layers.

### Client

Connection management.

### PDA

Canonical PDA derivation.

### Accounts

Account fetching and decoding.

### Instructions

Instruction builders.

### Transactions

Transaction assembly.

### Events

Event decoding.

### Utilities

Common helper functions.---

## 6. SDK Client

The primary SDK object is:

```typescript
BabycowansClient
```

Responsibilities:

- loads the IDL
- connects to Solana RPC
- exposes protocol APIs
- validates configuration

Applications normally create one client instance.

---

## 7. PDA Module

The SDK provides deterministic PDA helpers.

Examples:

```typescript
findProtocolConfig()

findAssetConfig()

findApplication()

findApplicationAsset()

findGatePolicy()

findRewardCampaign()
```

Applications never derive protocol PDAs manually.

---

## 8. Account Module

The SDK provides typed account fetchers.

Examples:

```typescript
getProtocol()

getAsset()

getApplication()

getApplicationAsset()

getGatePolicy()

getRewardCampaign()
```

Each function returns decoded protocol objects.

---

## 9. Instruction Builders

Every protocol instruction has one SDK builder.

Examples:

```typescript
initializeProtocol()

registerAsset()

registerApplication()

configureApplicationAsset()

createGatePolicy()

createRewardCampaign()

processPayment()

verifyGateAccess()
```

Builders construct instructions but never submit transactions.

---

## 10. Transaction Builder

The SDK provides transaction composition.

Example responsibilities:

- combine instructions
- estimate compute budget
- add priority fee
- attach signers
- serialize transaction

Transaction submission remains explicit.---

## 11. Event Module

The SDK provides strongly typed event decoding.

Examples:

```typescript
onProtocolInitialized()

onAssetRegistered()

onApplicationRegistered()

onPaymentProcessed()

onGateAccessVerified()

onRewardDistributed()
```

Applications should consume decoded events instead of parsing logs manually.

---

## 12. Error Handling

The SDK maps protocol errors into typed exceptions.

Example:

```typescript
try {
    ...
} catch (error) {
    if (error instanceof ProtocolPausedError) {
        ...
    }
}
```

Raw custom program errors should never be exposed directly to SDK consumers.

---

## 13. Token Support

The SDK automatically supports:

- SPL Token
- Token-2022

Applications never choose token instructions manually.

The SDK selects the correct implementation using the registered AssetConfig.

---

## 14. Payment API

Example interface:

```typescript
client.pay({
    application,
    asset,
    payer,
    amount
})
```

The SDK derives every required PDA automatically.

Applications only provide business inputs.

---

## 15. Gate Verification API

Example interface:

```typescript
client.verifyAccess({
    application,
    asset,
    wallet
})
```

The SDK returns a strongly typed verification result.

Applications never inspect raw accounts directly.---

## 16. Reward API

Example interface:

```typescript
client.createRewardCampaign({
    application,
    asset,
    campaign
})
```

Reward distribution APIs remain deterministic and fully typed.

---

## 17. Configuration

Example:

```typescript
new BabycowansClient({

    connection,

    programId,

    commitment

})
```

The SDK never relies on global mutable configuration.

---

## 18. Versioning

The SDK follows semantic versioning.

Example:

```text
1.0.0
1.1.0
1.2.0
2.0.0
```

Minor releases remain backward compatible.

Major releases may introduce new protocol capabilities.

---

## 19. Testing

The SDK includes:

- unit tests
- integration tests
- RPC tests
- local validator tests
- Token-2022 tests

Every public API must be covered by automated tests.

---

## 20. Performance

The SDK minimizes:

- RPC calls
- PDA derivations
- account decoding
- transaction size
- unnecessary allocations

Performance optimizations must never change observable behavior.

---

## 21. Security

The SDK never:

- stores private keys
- manages wallets
- bypasses protocol validation
- modifies protocol rules
- performs hidden RPC operations

Wallet authorization always remains external.---

## 22. Documentation

The SDK documentation includes:

- installation
- quick start
- account model
- instruction examples
- payment examples
- token gating examples
- reward examples
- migration guide
- API reference

Every public API must include executable examples.

---

## 23. Public API Stability

Once released, public SDK APIs should remain stable.

Breaking changes require:

- major version increment
- migration guide
- release notes
- compatibility documentation

---

## 24. Design Guarantees

The SDK guarantees:

1. Deterministic PDA derivation.
2. Strong typing.
3. Canonical instruction builders.
4. Automatic Token-2022 compatibility.
5. Stable public APIs.
6. Zero duplicated business logic.
7. Explicit transaction submission.
8. Deterministic account decoding.
9. Version-aware protocol support.
10. Complete documentation.

---

## 25. Version 1 SDK Scope

Version 1 includes everything required for a production application.

Applications should not require custom protocol wrappers.

The Babycowans SDK is intended to become the single official interface between developers and the Babycowans Protocol.
