# Babycowans Protocol Token-2022 Specification

## 1. Purpose

This specification defines how Babycowans Protocol supports Solana token programs.

Version 1 is designed to support both:

- SPL Token Program
- Token-2022 Program

without changing the public protocol API.

The protocol validates the token program for every registered asset and dispatches token operations accordingly.

---

## 2. Design Principles

The token layer must satisfy the following goals.

### Backward Compatible

Applications using legacy SPL Token remain fully supported.

### Forward Compatible

Applications using Token-2022 extensions remain supported without changing protocol architecture.

### Program Agnostic

Business logic never depends on a specific token program.

Instead, token operations are routed through the validated token program stored inside AssetConfig.

### Explicit Validation

Every instruction validates:

- mint owner
- token program
- mint decimals
- account ownership
- extension compatibility

No implicit assumptions are allowed.

---

## 3. Supported Token Programs

Version 1 supports:

### SPL Token Program

Used for:

- standard fungible tokens

### Token-2022 Program

Used for:

- extension-enabled fungible assets

The protocol stores which program owns every canonical mint.

---

## 4. Canonical Asset Registration

Each Babycowans asset stores:

- mint
- token program
- decimals
- asset domain
- protocol status

These values become immutable after registration except protocol status.

Changing mint ownership or token program requires a future protocol migration.---

## 5. Supported Extensions

Version 1 intentionally supports a conservative extension set.

Extensions that are compatible with the protocol include:

- Metadata Pointer
- Token Metadata
- Permanent Delegate
- Memo Transfer
- Transfer Hook (optional for applications)
- Group Pointer
- Group Member Pointer

The protocol validates extension compatibility during asset registration.

Unsupported extensions result in deterministic failure.

---

## 6. Unsupported Extensions

Version 1 does not depend on:

- Confidential Transfers
- Confidential Mint/Burn
- Interest Bearing Tokens
- Non Transferable Tokens
- Scaled UI Amount
- CPI Guard requirements imposed by third parties

Future protocol versions may add support without modifying Version 1 public interfaces.

---

## 7. Token Program Detection

Asset registration validates:

- mint owner
- executable token program
- expected program id

The detected program becomes part of AssetConfig.

Every later instruction uses this recorded value instead of trusting client input.

---

## 8. Payment Dispatch

The process_payment instruction selects the correct CPI automatically.

Pseudo flow:

```text
if token_program == SPL_TOKEN
    invoke SPL Token CPI
else if token_program == TOKEN_2022
    invoke Token-2022 CPI
else
    fail
```

Applications never need separate payment APIs.---

## 9. Transfer Hook Compatibility

The protocol itself never requires a Transfer Hook.

If an asset uses a Transfer Hook, the protocol:

- validates the configured token program
- forwards the CPI correctly
- propagates hook failures without modification

The protocol never bypasses extension logic.

---

## 10. Metadata

Version 1 never depends on token metadata for protocol execution.

Metadata may be used by:

- SDK
- Explorer
- Wallet integrations
- Developer tools

Protocol security never relies on metadata values.

---

## 11. Token Account Validation

Before every transfer the implementation validates:

- correct mint
- correct token program
- correct owner
- initialized account
- sufficient balance
- account state

Validation occurs before any CPI.

---

## 12. Decimal Handling

Amounts are always processed using raw on-chain units.

The protocol never performs floating-point arithmetic.

Display formatting belongs exclusively to:

- SDK
- API
- Frontend
- Wallet

The protocol always stores and transfers integer values.

---## 13. Security Model

The token layer guarantees:

- deterministic token program validation
- deterministic mint validation
- immutable asset registration
- CPI execution only through validated programs
- no dynamic program substitution
- no client-controlled token program selection

These guarantees prevent program spoofing attacks.

---

## 14. Future Compatibility

Future protocol versions may support additional Token-2022 extensions.

Adding support requires:

- specification update
- implementation
- SDK update
- tests
- release notes

The Version 1 public API remains unchanged.

---

## 15. Version 1 Guarantees

Version 1 guarantees:

1. Support for SPL Token.
2. Support for Token-2022.
3. Deterministic token program selection.
4. Canonical asset validation.
5. Extension-aware execution.
6. No dependency on metadata.
7. No dependency on wallet implementation.
8. Integer-only accounting.
9. Deterministic CPI dispatch.
10. Future compatibility without redesigning the protocol.
